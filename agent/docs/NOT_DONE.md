# 还没做的事（同步给队友）

MVP 的范围：流程完整、限制在代码里生效、输出格式对、证据可追溯。下面是**有意没做**或**没做完**的部分，以及原因。

## 1. 跨会议关联基本没找对（最重要的未完成项）

**现状**
- 在 TS3006 上，gold 有 8 条前后关联，系统一条没命中；系统自己找出的 2 条也不对。
- `prior_context_needed` 的召回很低（gold 里为 true 的条目，S2 只找到 1/6，S1 为 0/6）。
- 所以报告里 S2（读前序）相对 S1 没有明显优势，结论是"没有看出明显帮助"，不是"有帮助"。

**原因**
- agent 要一边判断 owner、deadline、证据，一边顺便找前序关联，任务太杂。
- 使用的模型较弱（gpt-5-nano），agent 写的检索词又长又杂，常搜不到。
- 关联的前提是当前会议的条目先抽对，而 actions 本身抽得不准，关联自然对不上。

**建议的做法（精简版，没有实现）**
- 加一个专门的"跨会议关联"步骤，不再靠 agent 顺带完成。
- 每场会议抽取完成后，把本场每个条目和同一系列更早会议里已记录的条目放在一起，让模型一次性判断关系：延续、更新、替换、取消、完成、解决，或没有关系。
- 每场只增加 1 到 2 次模型调用，比 agent 多次搜索便宜。
- 只能读更早的会议，限制仍由代码强制。
- 关联结果写进 `related_items`；有关联的条目才标 `prior_context_needed`。
- agent 保留，但职责收窄为查 owner、deadline 和证据。
- demo 用 TS3006 的 b→c。
- 粗估约 2 小时（写代码 1 小时、重跑 S2 15 到 30 分钟、评估和文档 30 分钟）。不保证有效果：如果仍然命中很低，就如实写进报告。

## 2. 目前只评估了 TS3006

**原因**
- 课程项目，控制工程量；TS3006 是 gold 里"动作多、跨会议变化清楚"的 demo 首选。
- 每个系列完整跑一遍要约 1.5 小时（S2、S1、B0、评估）。
- 样本很小：4 场会议、13 条 gold action、22 条决策、12 条问题，指标差几条就差很多。
- 提示词和阈值是看着 TS3006 调的，另用了 SB 全部 16 场 gold 的统计，所以 TS3006 上的数字偏乐观。

**要评估其他系列的做法（不碰 SC）**

```
.venv\Scripts\python scripts\run_series.py TS3004 s1 mvp

```
ES2011、IS1008 同理。注意：提示词里的示例来自 ES2011b、IS1008b、TS3004c（见 `docs/FEWSHOT_EXAMPLES.md`），评估这几个系列时要排除这些条目（TS3004 受影响最小，只有 c 的 2 条）。

## 3. 没有用 SC（ES2004、TS3007）

**原因**
- SC 是留出测试集，规则是设计冻结后只跑一次。现在还要继续调（关联、actions 等），提前跑会让最终结果不再干净。
- 看过 SC 结果后再改系统、再跑，这个数字就不能当作对新数据的真实估计。
- 代码里已有保护：跑 SC 要加 `--allow-sc`，评估和证据支持脚本遇到 SC 会拒绝。
- 具体的冻结和跑法见 `docs/HANDOFF.md`。
