# 留出测试集评估报告：ES2004 + TS3007

日期：2026-11-03 · 测试集：SC 留出集，2 个系列 × 4 场会议（a→d）· 模式：B0 / S1 / S2 · 每种模式各运行一次

## 结论

- **三种模式没有明显赢家。** 按三类条目合并计算的严格 F1：B0 0.41，S1 0.41，S2 0.35；容忍拆分/合并的 F1：B0 0.38，S1 0.39，S2 0.39。gold 总共只有 60 个条目，漏掉或多找到一个条目，召回率就变化约 1.7 个百分点，所以这些差别都在噪声范围内。
- **容忍指标没有整体抬高分数。** 它只让 S1/S2 的行动明显变好（F1 0.47 → 0.62 / 0.56）：系统常把一项 gold 任务拆成几条。其他格子里，容忍分数反而低于严格分数，因为两次判断彼此不一致：严格对齐中有 1–8 对，在容忍判断里没有链接（见 §3.1）。
- **前序会议上下文（S2）没有带来提升**，结论与开发集 TS3006 相同。S2 的决策和问题 F1 都低于 S1。跨会议关联 `related_items` 一个也没对上：S2 预测了 4 条，0 条正确，gold 有 5 条。gold 中需要前序上下文的条目，S1 和 S2 一条都没标出（`prior_context_needed` 0/2）。
- **决策是最弱的一类**（F1 0.25–0.38）。ES2004b 的 7 条 gold 决策在三种模式下都是 0 命中。
- **负责人（owner）准确率取决于系列。** TS3007 较好（4–6/6–7）；ES2004 在三种模式下都是 0。gold 把两项"全组一起做"的任务分给全部四位成员，系统要么留空，要么只指定一人。
- **证据支持度高，但摘要覆盖低。** LLM 判官认为 89%–92% 的条目陈述有引用对话支持。摘要的忠实度不低，但对 gold 摘要要点的覆盖只有 1.6–2.3 分（满分 5）。
- **成本差距大。** S1 平均每场 469 秒、约 41 万 token、43 次模型调用。S2 计入它复用的 S1 阶段后，是 590 秒、约 51 万 token、52 次调用，是三种模式中最贵的。B0 只要 94 秒、3.4 万 token、2 次调用，token 少 12–15 倍，F1 却相当。

## 2. 评分方法

- **条目对齐（严格）**：LLM 判官把系统条目与 gold 条目一对一对齐。容忍拆分/合并的多对多指标见 §3.1。每个条目列表判 3 次，按多数票计。所有模式共用同一份缓存，相同的条目列表得到相同的对齐结果。
- **判官**：与流水线是同一个 gpt-5-nano（项目默认 `MTA_JUDGE=pipeline`）。共 251 次调用，约 98 万 token。
- 少样本示例来自开发集，SC 中没有需要排除的 gold 条目。
- **证据支持**：判官只看条目陈述和它引用的对话行，判断"支持 / 部分支持 / 不支持"。
- **摘要**：忠实度只对照转录稿打分（1–5）；覆盖度对照 gold 摘要要点打分（1–5）。判官不知道摘要出自哪个系统。

### 3.1 容忍拆分/合并的匹配（新增指标，与严格指标并列）

**规则：**
- 判官对每一对（系统条目，gold 条目）判断关系，分三种：
  - **相同**：同一件事，只是措辞不同；
  - **拆分**：系统条目是 gold 条目中一个实质性的部分；
  - **合并**：系统条目同时覆盖几条 gold。
- 只是话题相关、内容不同的，不算匹配。允许多对多链接。
- 精确率 = 至少链接到一条 gold 的系统条目数 ÷ 系统条目总数；召回率 = 至少被一条系统条目覆盖的 gold 数 ÷ gold 总数。
- **纯重复照样扣分**：同一条 gold 被两条系统条目完整地各说了一遍（都判成"相同"）时，只算记录顺序中的第一条，其余记为误报。拆成几个互补部分的不扣分。
- 其他规则与严格指标相同：3 票多数，各类型分开算，判官仍是 gpt-5-nano。
- 负责人准确率按链接上的行动对统计，每条链接算一对。

**投票细节：** 一对条目在至少 2/3 次判断中被链接（关系不限）才算链接。至少 2 票判"相同"时记为相同，否则取拆分/合并中票数多的一种，平票记为拆分。若重复的系统条目还有别的有效链接，它仍算已链接，不记为误报。

P / R / **F1**，括号内为 已链接系统条目 / 系统条目，被覆盖 gold / gold。

| B0 | 0.35 / 0.60 / **0.44** (9/26, 9/15) | 0.29 / 0.38 / **0.33** (10/34, 11/29) | 0.35 / 0.44 / **0.39** (6/17, 7/16) | **0.38** | 6/9 = 0.67 |

按系列的合并 F1（严格 → 容忍）：

| 系列 | B0 | S1 | S2 |
|---|---|---|---|
| ES2004 | 0.30 → 0.30 | 0.33 → 0.34 | 0.29 → 0.32 |

**两种指标的判断并不一致。** 两者都由 gpt-5-nano 判断，但分别独立调用。按定义，严格指标的每一对匹配都应该至少是容忍指标里的"相同"链接，实际上：
- B0 严格 28 对中有 24 对也被链接，S1 28 对中有 20 对，S2 25 对中有 24 对；
- 另有 4–9 条链接只在容忍判断中出现。

抽查严格多出来的匹配，有些明显不对。例如 TS3007c 的"游戏和语音识别是可选功能"被严格匹配到"小组采纳了游戏功能"，容忍判官没有链接这一对。因此，两种指标之间的差别有一部分是判官噪声，不完全来自拆分/合并。我没有强行把严格匹配并入容忍链接，那样会改变指标定义。若改用更强的判官（如 Claude），这种不一致预计会减少。

- 调用次数和 token：S2 自身的用量，加上 S1 在这四个阶段的用量（取自 S1 的 `run.json` 分阶段统计）；

## 8. 主要错误

1. **决策漏检集中在 ES2004b**：7 条 gold 决策三种模式都没找到。S1/S2 在这场一条决策都没输出，B0 只输出 1 条且未对上。
2. **全组负责人**：ES2004a/d 中"全组准备下次会议"和"全员填写评估问卷"在 gold 中分给 4 位成员，系统给出 `null`（ambiguous）或只给一人。
3. **决策过度输出**：S1/S2 在 TS3007 输出 19–20 条决策，gold 只有 11 条，精确率仅 0.20 左右。
4. **跨会议关联无效**：S2 预测的 4 条关联全部错误，gold 中的 5 条一条都没找到。

## 9. 局限

- 每种模式只运行一次。项目记录显示同一输入在多次运行之间波动很大（例如 B0 在开发集上的决策 F1 从 0.11 到 0.53）。
- 判官与被测模型是同一个 gpt-5-nano，可能存在自我评判偏差；摘要的校准结果已经说明它不可靠。如需更可信的数字，可以在 `.env` 中设置 `MTA_JUDGE=claude`（需要 `ANTHROPIC_API_KEY`）重新评分。这只重跑评分，不需要重跑系统。
- 没有 git commit，冻结版本靠源码指纹标识。
- 证据支持的人工抽查尚未进行。
- 容忍指标是在看到 SC 严格结果之后新增的评分方式，只改评分，不改被测系统，SC 结果仍然干净。新增代码：`src/mta/evaluate.py`（`make_tolerant_matcher`、`vote_links`、`drop_duplicates`、`tolerant_prf`）、`scripts/full_eval.py`（`tolerant_extraction`，并写入 EVALUATION.md 表格）、`tests/test_tolerant_match.py`（6 个离线测试）。这些改动让源码指纹不再等于本次运行记录的 `20d256c7…`。运行记录本身不受影响，之后的新运行会记录新的指纹。
- 容忍评分新增 171 次判官调用；严格、证据支持和摘要的判断全部来自缓存，重跑后数字不变（已核对）。
- 离线测试：设置 `PYTHONUTF8=1` 后 457/458 通过。唯一的失败是目录不是 git 仓库，与被测逻辑无关。
